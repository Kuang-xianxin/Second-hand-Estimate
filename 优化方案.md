## 一、技术选型（高并发架构）

### 1.1 选型原则

- 并发量未知但目标高性能，按能支撑高并发去设计
- 不引入过度复杂的架构，但基础设施必须到位
- 每个组件都有明确的扩容路径

### 1.2 核心技术栈


| 层级                | 组件                             | 选型  | 说明                                                                    |
| ----------------- | ------------------------------ | --- | --------------------------------------------------------------------- |
| **L1 缓存**         | Redis                          | 必选  | 替代 Python dict，支持多 Worker 共享，进程重启不丢热点数据，并发读写 QPS ~10万/s               |
| **L2 缓存 + 主力数据库** | PostgreSQL                     | 必选  | 替代 SQLite，真并发读写（MVCC），支持千万级数据，支持 JSON/JSONB 扩展字段                      |
| **数据库驱动**         | asyncpg + SQLAlchemy 2.0 async | 必选  | 替换 aiosqlite，异步连接池，与 FastAPI/Starlette 原生配合                           |
| **数据库连接池**        | PgBouncer（事务模式）                | 推荐  | 100 个真实 PG 连接 → 支撑 1000+ 并发请求；内存占用极低（几 MB）；也可先用 SQLAlchemy 内置 pool 过渡 |
| **定时任务锁**         | Redis SETNX / Redlock          | 必选  | 多 Worker 时防定时任务重复执行，确保同一时刻只有一个人物运行                                    |
| **后端服务器**         | Uvicorn 多 Worker               | 必选  | 单 Worker 无法利用多核；建议 4-8 个 Worker，配合 Nginx 负载均衡                         |
| **反向代理 + 负载均衡**   | Nginx（已有）                      | 保留  | 将请求分发到多个 Uvicorn Worker 端口，静态资源缓存，SSL 终端                              |


### 1.3 为什么不用 MySQL

MySQL 和 PostgreSQL 在这个场景下都可以用，选 PostgreSQL 的原因：

- **JSON 支持**：PostgreSQL 的 JSONB 比 MySQL 的 JSON 更成熟，索引和查询都更快
- **全文搜索**：PostgreSQL 内置全文搜索，未来做商品标题检索不需要额外组件
- **COPY 批量导入**：PostgreSQL 的 `COPY` 命令比 MySQL 的 `LOAD DATA` 更易用，批量写入更快
- **异步生态**：Python asyncpg 比 MySQL async 驱动更成熟、稳定

### 1.4 为什么不用 Redis 作为主力数据库

Redis 是内存数据库，受限于内存大小（几十 GB 算很大了），且：

- 不擅长关系查询（商品按 keyword 聚合、按 brand 筛选等）
- 持久化（AOF/RDB）有数据丢失风险
- 无事务隔离，多步操作需要 Lua 脚本
- 不支持复杂索引

Redis 做 L1 缓存是它的正确位置，不越界做主力 DB。

### 1.5 三级缓存架构（最终版）

```
┌─────────────────────────────────────────────────────────────────────────┐
│                         三级缓存分层架构图                                   │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  用户请求 ──▶ L1 Redis（最快）──▶ L2 PostgreSQL（主力）──▶ L3 历史趋势兜底 │
│                   │                    │                    │         │
│                < 1ms                 5-20ms               20-50ms       │
│             10000 条              852 条               25560 条        │
│             内存 KV               关系型DB             关系型DB         │
│             多 Worker 共享         持久化               持久化           │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

**L1 vs L2 职责分离**：


| 维度   | L1 Redis               | L2 PostgreSQL          |
| ---- | ---------------------- | ---------------------- |
| 存储形态 | 内存 KV（JSON 序列化）        | 关系型表                   |
| 持久化  | 可选（RDB/AOF），丢失可从 L2 恢复 | 强持久化                   |
| 并发能力 | ~10万 QPS               | ~1万 QPS（单 PG 实例）       |
| 存储内容 | 热门型号估价结果的热点快照          | 全部 852 个型号的完整数据 + 历史趋势 |
| 过期策略 | TTL 1.5 小时（与爬取周期同步）    | 长期保留，定期清理历史            |
| 适用场景 | 热点数据闪电读（< 1ms）         | 全量数据可靠存储               |


### 1.6 Redis L1 缓存的具体收益

**不用 Redis（Python dict L1）的问题**：

- 多个 Uvicorn Worker 之间各自维护一份 dict，数据不一致
- 进程重启后 dict 全部丢失，缓存击穿，瞬间大量请求打到 PG
- 热门型号被反复查询，无法跨 Worker 共享，热数据利用率低

**用 Redis 后的收益**：

- 多 Worker 共享同一份热数据，缓存命中率更高
- 进程重启后 Redis 数据还在，用户无感知
- 支持 TTL 自动过期，与爬取周期完美对齐
- 支持 `INCR`/`DECR` 做计数（如缓存访问计数、API 限流）
- 支持分布式锁（定时任务防重）
- 延迟 < 1ms，比查 PG 快 10-50 倍

## 二、项目现状与目标

### 现状问题

- 每次估价需要等待 45-90 秒（实时爬取 + AI 分析），用户体验差
- 捡漏逻辑不清晰：估价结果页和捡漏广场都存在，但没有区分「条件捡漏」和「全局捡漏」
- 当前 `bargain_alerts` 表只在用户主动估价时才写入，全局捡漏无数据来源

### 优化目标


| 指标          | 当前        | 目标                       |
| ----------- | --------- | ------------------------ |
| 用户响应时间      | 45-90 秒   | **< 500ms**（查缓存）         |
| 爬取方式        | 用户请求时触发   | **每 1.5 小时后台自动全量**       |
| 条件捡漏        | 无         | 用户搜索某型号后，**该型号有捡漏才显示**   |
| 全局捡漏（捡漏广场）  | 仅有历史估价触发  | **独立运营，每 1.5 小时随爬取自动更新** |
| 全量 CCD 型号覆盖 | 已知 ~852 个 | ~852 个型号全部覆盖             |

## 二、核心概念：两种捡漏机制

本系统存在 **两种性质完全不同的捡漏**，必须严格区分：

```
┌─────────────────────────────────────────────────────────────┐
│                   条件捡漏（Conditional Bargain）              │
│                                                             │
│  触发条件：用户搜索某个具体型号（如「索尼 T700」）                  │
│  数据来源：从该型号爬取到的商品中检测                                │
│  显示位置：估价结果页底部（HomeView.vue 的 bargains 区块）           │
│  显示规则：该型号的爬取结果中有捡漏才显示，没有则不显示                  │
│  数据表：bargain_alerts 表（keyword 字段关联型号）                  │
│  刷新方式：随用户搜索时实时计算（复用爬取数据，不额外爬取）              │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│                   全局捡漏（Global Bargain）                   │
│                                                             │
│  触发条件：后台定时任务，每 1.5 小时自动执行                        │
│  数据来源：从全部 ~852 个 CCD 型号的爬取商品中检测                   │
│  显示位置：独立「捡漏广场」页面（BargainView.vue 改造）              │
│  显示规则：展示全站所有 CCD 型号中的捡漏商品，**不区分型号**             │
│  排序规则：**按利润从高到低排序**                                 │
│  数据表：global_bargains 表（新增）                              │
│  刷新方式：随定时爬取自动更新，用户无需任何操作                       │
└─────────────────────────────────────────────────────────────┘
```

### 两种捡漏对比


| 维度   | 条件捡漏          | 全局捡漏（捡漏广场）      |
| ---- | ------------- | --------------- |
| 触发方式 | 用户搜索具体型号      | 后台定时任务自动        |
| 数据来源 | 当前搜索型号的爬取结果   | 全部 852 个型号的爬取结果 |
| 显示位置 | 估价结果页底部       | 独立的「捡漏广场」Tab    |
| 显示条件 | **该型号有捡漏才显示** | **始终显示**（有数据时）  |
| 排序方式 | 按利润降序         | **按利润从高到低**     |
| 型号限制 | 仅当前搜索型号       | **不限型号**，跨品牌跨型号 |
| 数据更新 | 随用户搜索更新       | 每 1.5 小时随爬取自动更新 |
| 用户操作 | 无需操作          | 无需操作，完全自动化      |

## 四、三级缓存详解

### 4.1 为什么需要三级缓存

缓存的本质是「用空间换时间」，不同层级的缓存有不同的访问速度和容量：

```
┌──────────────────────────────────────────────────────────────────────┐
│                    三级缓存分层架构图                                       │
├──────────────────────────────────────────────────────────────────────┤
│                                                                      │
│  用户请求 ──▶ L1 Redis（最快）──▶ L2 PostgreSQL（主力）──▶ L3 历史趋势 │
│                   │                    │                    │          │
│                < 1ms                 5-20ms               20-50ms      │
│              10000 条               852 条               25560 条       │
│              内存 KV              关系型表              关系型表         │
│           多 Worker 共享            持久化                持久化        │
│           TTL 1.5h 自动过期                                                 │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘
```

### 4.2 三级缓存职责说明

#### L1：Redis 缓存（最热数据）

- **存储介质**：Redis 内存 KV（`asyncpg` / `redis-py` 异步客户端）
- **访问速度**：< 1ms
- **存储内容**：热门型号的估价结果快照（JSON 序列化），TTL 1.5 小时
- **跨 Worker 共享**：所有 Uvicorn Worker 共用同一份 Redis 数据
- **进程重启安全**：Redis 数据持久在内存，Worker 重启不影响
- **防缓存击穿**：热门数据持续在 Redis 中，不会因重启导致雪崩
- **适用场景**：用户反复查询同一热门型号（如 IXUS 130、T700）

**L1 缓存 key 设计**：

```
ccd:val:{keyword}       → 估价结果 JSON（TTL 1.5h）
ccd:val:list            → 全部 keyword 列表（用于批量预热）
ccd:lock:crawl          → 分布式锁（定时任务防重）
ccd:rate:{ip}           → API 限流计数（TTL 1min）
```

**L1 缓存实现示例**：

```python
import redis.asyncio as redis
import json
from typing import Optional

_redis: Optional[redis.Redis] = None

async def get_redis() -> redis.Redis:
    global _redis
    if _redis is None:
        _redis = redis.from_url("redis://localhost:6379/0", decode_responses=True)
    return _redis

async def get_cache_l1(keyword: str) -> Optional[dict]:
    r = await get_redis()
    data = await r.get(f"ccd:val:{keyword}")
    if data:
        return json.loads(data)
    return None

async def set_cache_l1(keyword: str, data: dict, ttl: int = 5400):
    r = await get_redis()
    await r.setex(f"ccd:val:{keyword}", ttl, json.dumps(data, ensure_ascii=False))

async def invalidate_cache_l1(keyword: str):
    r = await get_redis()
    await r.delete(f"ccd:val:{keyword}")
```

#### L2：PostgreSQL 数据库缓存（主力缓存）

- **存储介质**：PostgreSQL `ccd_price_cache` 表
- **访问速度**：5-20ms
- **存储内容**：全部 852 个型号的完整缓存数据
- **生命周期**：持久化，1.5 小时刷新一次
- **工作原理**：L1 未命中时查数据库，命中则写入 L1
- **适用场景**：所有型号的估价查询，L1 未命中时兜底

#### L3：价格历史趋势（辅助数据）

- **存储介质**：PostgreSQL `price_history` 表
- **访问速度**：~20-50ms
- **存储内容**：每次爬取的价格快照，保留最近 30 次（约 45 天）
- **生命周期**：持久化，长期保留
- **工作原理**：查询时附加历史趋势信息（价格涨了还是跌了）
- **适用场景**：给用户提供价格趋势参考（附加价值，非必需）

### 4.3 缓存查询流程

```
用户输入 keyword
      │
      ▼
┌─────────────────────────┐
│  1. 查 L1（Redis）       │  < 1ms
│     命中？                │
└────────┬────────────────┘
         │ 是                 │ 否
         ▼                   ▼
   直接返回              ┌─────────────────┐
   (< 1ms)              │ 2. 查 L2（PG）   │  5-20ms
   + 写入 L1 预热        │ ccd_price_cache │
                        └────────┬────────┘
                                 │ 是                 │ 否
                                 ▼                   ▼
                          写入 L1              触发实时爬取
                          返回缓存              （走旧逻辑）
                          (5-20ms)
```

### 4.4 缓存预热策略

定时任务爬取完成后，将热门型号批量写入 Redis L1，避免用户请求冷启动：

```python
async def warm_cache_l1(top_keywords: list[str]):
    """爬取完成后，将热门型号预热到 Redis L1"""
    r = await get_redis()
    pipe = r.pipeline()
    for kw in top_keywords:
        # 从 PG 读出热门型号，写入 Redis
        data = await db.fetch_one(...)  # 查 L2
        if data:
            pipe.setex(f"ccd:val:{kw}", 5400, json.dumps(dict(data), ensure_ascii=False))
    await pipe.execute()
```

## 五、数据库表结构设计（PostgreSQL）

> **重要变更**：从 SQLite 升级为 PostgreSQL，DDL 语法全部使用 PostgreSQL 格式。
> 连接方式：`asyncpg` + SQLAlchemy 2.0 async，连接字符串格式：`postgresql+asyncpg://user:pass@host:5432/dbname`

### 5.1 迁移说明

```
SQLite (.db 文件)  ──▶  PostgreSQL (腾讯云服务器)
aiosqlite           ──▶  asyncpg
单文件，进程级锁      ──▶  C/S 架构，真并发 MVCC
```

**迁移步骤**：

1. 腾讯云安装 PostgreSQL（`apt install postgresql`）
2. 创建数据库和用户
3. 修改 `backend/.env` 中的数据库连接字符串
4. 执行新建表 SQL（`CREATE TABLE IF NOT EXISTS` 自动幂等）
5. 原有 SQLite 数据可用 `pg_loader` 或手动脚本迁移（可选，非必须）

**PgBouncer 配置（连接池）**：

```ini
; /etc/pgbouncer/pgbouncer.ini
[databases]
ccd_app = host=127.0.0.1 port=5432 dbname=ccd_db

[pgbouncer]
pool_mode = transaction
max_client_conn = 1000
default_pool_size = 20
```

连接字符串改为：`postgresql://user:pass@127.0.0.1:6432/ccd_db`

**缓存查询逻辑**：

```python
import redis.asyncio as redis
import json

async def get_valuation_from_cache(keyword: str) -> Optional[dict]:
    """
    三级缓存查询：
    1. L1: Redis（< 1ms）
    2. L2: PostgreSQL ccd_price_cache（5-20ms）
    3. 兜底: 返回 None，触发实时爬取

    返回格式：
    {
        "from_cache": True,
        "keyword": "...",
        "base_price": 350.0,
        "price_min": 280.0,
        "price_max": 450.0,
        "sample_count": 25,
        "is_xd_card": False,
        "crawled_at": "2026-05-12T14:30:00",
        "cache_level": "L1",   # 或 "L2"
    }
    """
    # L1: Redis
    r = await redis_client.get_redis()
    raw = await r.get(f"ccd:val:{keyword}")
    if raw:
        return json.loads(raw)

    # L2: PostgreSQL
    record = await db.fetch_one(
        "SELECT * FROM ccd_price_cache WHERE keyword = :kw",
        {"kw": keyword}
    )
    if record:
        data = dict(record)
        # 回填 L1
        await r.setex(f"ccd:val:{keyword}", 5400, json.dumps(data, ensure_ascii=False))
        return data

    return None
```

### 7.3 全局捡漏检测算法

```python
def detect_global_bargains(all_items: list[CrawledItem], keyword_prices: dict[str, float]) -> list[GlobalBargain]:
    """
    全局捡漏检测：从全部爬取商品中检测所有型号的捡漏机会。

    检测逻辑：
    1. 遍历全部 crawled_items
    2. 按 keyword 找到对应型号的基准价
    3. 满足捡漏条件 → 加入全局捡漏列表
    4. 全量替换 global_bargains 表
    """
    global_bargains = []

    for item in all_items:
        if item.sold or not item.is_valid:
            continue

        base_price = keyword_prices.get(item.keyword, 0)
        if base_price <= 0:
            continue

        profit = base_price - item.price

        # XD 卡叠加（复用现有 bargain.py 逻辑）
        xd_bonus = detect_xd_bonus(item)  # (card_size, card_value)
        total_profit = profit + xd_bonus.card_value

        # 捡漏阈值：总利润 >= 基准价的 30% 或绝对利润 >= 80 元
        if total_profit < 80 and (profit / base_price) < 0.3:
            continue

        global_bargains.append(GlobalBargain(
            item_id=item.item_id,
            keyword=item.keyword,
            brand=extract_brand(item.keyword),
            title=item.title,
            current_price=item.price,
            base_price=base_price,
            profit_estimate=total_profit,
            discount_rate=round(total_profit / base_price, 3),
            quality_score=item.quality_score,
            is_xd_card=bool(xd_bonus.card_value),
            xd_card_size=xd_bonus.card_size,
            xd_card_value=xd_bonus.card_value,
            url=item.url,
            image_url=extract_first_image(item.images),
        ))

    # 按利润降序排序
    global_bargains.sort(key=lambda x: x.profit_estimate, reverse=True)
    return global_bargains
```

## 九、API 改造方案

### 9.1 改造后的估价 API 逻辑

```
用户输入 keyword
      │
      ▼
┌─────────────────────────┐
│  1. L1 缓存查询（Redis）│  < 1ms
└────────┬────────────────┘
         │ 命中                │ 未命中
         ▼                    ▼
    ┌─────────────┐      ┌─────────────────┐
    │  2. 检查新鲜度 │      │ 3. L2 缓存查询  │  5-20ms
    │  缓存 < 1.5h？ │      │ PostgreSQL     │
    └──────┬──────┘      └────────┬────────┘
           │                      │ 命中             │ 未命中
           │ 是                   ▼                  ▼
           │                写入 L1            触发实时爬取
           │                返回缓存              （走旧逻辑）
           │                (5-20ms)
           否
           │
           ▼
    返回旧缓存 + 异步更新
    （后台静默刷新，不阻塞用户）
```

### 9.2 关键行为说明


| 场景      | 行为                          |
| ------- | --------------------------- |
| 缓存命中且新鲜 | 直接返回缓存数据（< 1ms），无爬取，无 SSE   |
| 缓存命中但过期 | 返回旧数据，后台异步刷新缓存（用户无感知）       |
| 缓存未命中   | 触发实时爬取（走旧逻辑），爬取完成后存入缓存      |
| 定时任务进行中 | 用户请求时返回旧缓存（不阻塞），定时任务完成后自动更新 |

## 十二、LLM 调用策略（成本控制）


| 场景            | 是否调用 LLM | 说明                       |
| ------------- | -------- | ------------------------ |
| 后台定时任务        | **否**    | 纯规则估价（IQR + 加权中位数），成本 ¥0 |
| 用户主动估价（查库命中）  | **否**    | 直接返回缓存结果，无 LLM 调用        |
| 用户主动估价（缓存未命中） | **是**    | 实时爬取后调用多模型分析（作为辅助参考）     |
| 条件捡漏检测        | **否**    | 复用爬取数据，纯规则检测             |


**月度成本估算**：


| 模式             | 每小时  | 每日（12h） | 月度         |
| -------------- | ---- | ------- | ---------- |
| 纯规则（后台 + 缓存命中） | ¥0   | ¥0      | **¥0**     |
| 用户查询未命中（LLM）   | ~¥11 | ¥130    | **¥3,900** |


> **说明**：用户查询命中缓存时完全无 LLM 调用。未命中时才触发实时爬取+LLM。若 80% 的查询命中缓存，月成本从 ¥3,900 降至 **~¥780**。
